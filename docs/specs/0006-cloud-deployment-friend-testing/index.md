# 0006. Cloud deployment for friend testing

**Date**: 2026-08-25
**Updated**: 2026-09-09
**Status**: In Progress

## Summary

Vermouth will run on the existing Azure VM through its existing one node k3s installation. The VM has 2 CPUs and 8 GiB of memory, uses packaged Traefik for HTTPS, pulls private Docker Hub images by digest, and keeps state on the dedicated Azure disk when available. GitHub Actions builds and deploys only after manual confirmation, while local Task commands provide inspection, export, restore, and rollback. Before it tests a migration, the workflow reads the active Helm release through the restricted SSH path and records that exact starting point in the release bundle. Backup encryption and decryption use one explicit private identity that never leaves the operator Mac.

## Requirements

**User stories**:

1. As the operator, I want friends to reach Vermouth through a stable secure address so they can test the real sign in and invoice flow.
2. As the operator, I want development and production to use the same k3s, Traefik, Helm, image, migration, and health model so a production release is not a second platform.
3. As the operator, I want deployment failure to keep the previous application and data intact so recovery begins from a working release.
4. As the operator, I want a free manual export to my Mac so the lack of paid backup does not mean there is no recovery path at all.
5. As the operator, I want disaster recovery to restore the exact release evidence as well as the data so later status, deployment, and rollback commands still have one trusted history.

## Decision

**Chosen option**: Option 1: Existing Azure VM with k3s, packaged Traefik, private Docker Hub images, and a dedicated data disk

Reuse the inspected `Standard_D2ads_v6` VM and its existing k3s installation. Align local k3d to the production k3s version and packaged Traefik, promote one two architecture image set through private Docker Hub, deploy through manually triggered GitHub Actions and a restricted temporary SSH command, and keep production state under one recorded local storage root. Production image tags shorten only the source Git SHA to 12 characters and retain the full 64 character build input SHA256.

**Migration compatibility baseline**: the unique live deployed `vermouth` Helm revision, proven through its stored release identity and immutable release evidence, is the sole authority for `previous_application_revision`. GitHub reads it through restricted `inspect-base` after candidate image verification and the root deploy path resolves it again while holding the exclusive production lock before application state may change.

**Rate limit launch evidence**: feature 21 owns the schema, the only producer, and the only working path. `task test:auth-rate-limit` writes `.tmp/production/rate-limit-evidence.json` through the `write` mode of `gateway/cmd/ratelimitevidence`. The production workflow uses the command's `verify` mode against candidate production values, then consumes those exact bytes. It never copies or translates another evidence file.

**Backup identity contract**: `PROD_AGE_IDENTITY` is the absolute path to one native `age` identity file kept only on the operator Mac. `age-keygen -y` must derive exactly `PROD_AGE_RECIPIENT` from it before export or restore may contact the VM. Export authenticates and validates its encrypted result through pipes before the final atomic rename. Restore decrypts locally and sends the compressed plaintext only through pinned SSH to a protected short lived VM staging file. The private identity contents and path never enter Git, GitHub, the VM, Kubernetes, a release bundle, or an export archive (basis: official `age` and `age-keygen` command behavior, least privilege secret handling).

### Platform topology

| Resource | Choice | Ownership |
|---|---|---|
| VM | Existing Azure `Standard_D2ads_v6`, 2 CPU, 8 GiB, Ubuntu 24.04 | Azure and operator |
| Kubernetes | Existing one node k3s `v1.36.3+k3s1` | systemd `k3s` service |
| Edge | One packaged Traefik v3 replica | k3s packaged Helm release plus committed `HelmChartConfig` |
| Images | Private Docker Hub OCI image indexes, selected by root digest | GitHub Actions builds, k3s pulls |
| Application | Existing `vermouth-foundation` and `vermouth` releases | Repository Helm chart |
| Data | Eight static local PVs for four Postgres instances, Redpanda, Garage metadata and data, and Traefik ACME | StorageClass `vermouth-local` under the selected root |
| Secrets | Root owned production file to immutable Kubernetes Secrets | Task creates, Helm references names only |
| Public name | Azure Public IP DNS label | Azure Public IP configuration |
| Recovery | Encrypted manual export to the operator Mac | Task over operator SSH, with the private `age` identity kept on the Mac |

There is no application schema change.

The fixed production image inventory is `gateway`, `identity`, `teaching`, `billing`, `notifications`, `web`, `garage-init`, `identity-migration`, `teaching-migration`, `billing-migration`, and `notifications-migration`. The development token image is local only and never enters Docker Hub production promotion.

`pkg/vermouth/cmd/platformconfig production-image-plan <repository-root> <workload> <source-revision> <dockerhub-namespace>` is the sole producer of production image identity. It accepts only the fixed 11 workload names, requires `source-revision` to equal the full commit returned by `git rev-parse --verify HEAD^{commit}`, and rejects a dirty Git state in the Dockerfile, `.dockerignore`, declared inputs, or image lock. It reuses the versioned `vermouth-image-v1` canonical byte stream and per workload input inventory from spec 0005, including normalized repository paths, permission bits, file bytes, sorted build arguments, sorted base locks, sorted declared inputs, and the hash input platform order `linux/arm64`, then `linux/amd64`. The hash is independent of the runner architecture and emits exactly 64 lowercase hexadecimal characters. Its canonical JSON output contains `workload`, `dockerfile`, `target`, `repository`, `source_revision`, `build_input_sha256`, `tag`, `platforms`, `build_args`, and `base_locks`. Its output `platforms` field is normalized to `["linux/amd64","linux/arm64"]`. Unknown fields fail.

The canonical production tag is `git-<source_revision[0:12]>-<build_input_sha256>`. `source_revision` is the full 40 character Git SHA and `build_input_sha256` is the full output from the production image plan. The tag is 81 characters. The shorter `multi-<12 character input hash>` convention from spec 0005 remains local only and is never used for production promotion.

Production output is one root `application/vnd.oci.image.index.v1+json` document with exactly two runnable child descriptors. The children are one `application/vnd.oci.image.manifest.v1+json` manifest for `linux/amd64` and one for `linux/arm64`. Descriptor order is not significant during validation. The normalized `platforms` array in generated state is always `["linux/amd64","linux/arm64"]`. Buildx provenance and SBOM attestations are disabled for this workflow, so the root index contains no attestation or unknown descriptor.

The root image index and both child manifests carry OCI annotations `org.opencontainers.image.source`, `org.opencontainers.image.revision`, `org.opencontainers.image.created`, `vermouth.dev/workload`, and `vermouth.dev/build-input-sha256`. The source annotation is exactly `https://github.com/<GITHUB_REPOSITORY>` using the workflow repository slug. The revision annotation is the full source revision. One RFC 3339 UTC timestamp with whole seconds and `Z` is captured before a new workload build and copied byte for byte to all three documents.

Every Docker Hub production repository must protect `git-*` with an immutable tag rule before publication. The workflow uses concurrency group `production-<GITHUB_REPOSITORY>` with cancellation disabled from publication through final deployment. It resolves an existing tag to the authoritative root digest, fetches the root index by digest, requires the exact OCI media types and two platform descriptors above, fetches both child manifests by digest, then compares identity annotations byte for byte. Repository, full source revision, full build input SHA256, workload name, source URL, and the exact platform set must match. The created annotation must be present, valid, and identical across the three documents. A reused image preserves that value in `images.json`. When an immutable push loses a race, the workflow runs this same inspection against the winning tag and either reuses the matching index or reports a collision. A missing value, extra descriptor, changed child digest, or mismatch fails before VM contact. The workflow never deletes or replaces the existing tag.

### Production Traefik contract

K3s owns the only Traefik release. Task renders `deploy/platform/traefik/values-common.yaml` plus `values-production.yaml` into HelmChartConfig `traefik` in `kube-system`. Common values match spec 0005. Production values add the following exact behavior:

1. EntryPoints `web` on port 80 and `websecure` on port 443 are exposed by the existing Traefik LoadBalancer Service.
2. EntryPoint `web` redirects to `websecure` with HTTPS and permanent status, while Traefik handles `/.well-known/acme-challenge/` before redirect.
3. Resolver `letsencrypt-staging` uses HTTP challenge on `web`, the Let’s Encrypt staging directory, and `/data/acme-staging.json`.
4. Resolver `letsencrypt-production` uses HTTP challenge on `web`, the Let’s Encrypt production directory, and `/data/acme.json`.
5. Both resolvers use `PROD_ACME_EMAIL`. Files live on claim `traefik-acme`, mounted at `/data`, and remain mode `0600`.
6. A temporary staging probe Ingress for `PROD_HOSTNAME` must obtain and serve the staging certificate once. Task then removes it and the final application Ingress selects `letsencrypt-production`.
7. The final Ingress uses `spec.ingressClassName=traefik` plus annotations `traefik.ingress.kubernetes.io/router.entrypoints=websecure`, `traefik.ingress.kubernetes.io/router.tls=true`, and `traefik.ingress.kubernetes.io/router.tls.certresolver=letsencrypt-production`.

The application chart keeps `values.yaml` as common defaults, `values-local.yaml` for `vermouth.localhost`, and `values-production.yaml` for public deployment. Production values require `PROD_HOSTNAME`, enable the final Ingress and TLS annotations above, set runtime config to `{"schemaVersion":1,"environment":"production","googleAuthEnabled":true,"apiBasePath":"/api"}`, select StorageClass `vermouth-local`, require `dockerhub-pull`, and contain image digests plus Secret names only. Secret values never enter any Helm values file.

### Runtime Secret identity and evidence

Production uses the runtime Secret inventory and hash algorithm from spec 0005 without variation. The five name bases are `gateway-runtime`, `identity-runtime`, `teaching-runtime`, `billing-runtime`, and `notifications-runtime`. Google auth is enabled in production, so the identity key set includes `IDENTITY_GOOGLE_CLIENT_ID` and `IDENTITY_GOOGLE_CLIENT_SECRET`. Database URLs use the production service DNS names and decoded production password, while every other value comes from the named field in `/etc/vermouth/production.env`.

For one service, `vermouth-platformconfig secret-hash` receives the exact decoded JSON key and value map that Kubernetes receives. Keys sort by raw UTF8 bytes. The canonical stream starts with `vermouth-secret-v1`, then appends each four byte big endian key length, key bytes, four byte big endian value length, and value bytes. SHA256 over that stream is the full lowercase source hash. The name is `<nameBase>-<first-12-lowercase-source-sha256>` in namespace `vermouth`.

Every stable foundation Secret and runtime Secret is `immutable=true` and carries annotation `vermouth.dev/source-sha256=<full-source-sha256>`. Runtime Secrets also carry labels `app.kubernetes.io/name=vermouth`, `app.kubernetes.io/component=runtime-secret`, and `vermouth.dev/runtime-service=<service>`. Foundation Secrets keep their fixed foundation component label. The hash annotation is metadata, not a secret, and namespace RBAC remains the trust boundary that prevents untrusted metadata reads.

Generated Helm values store a fixed `release.runtimeSecrets` map with exactly `gateway`, `identity`, `teaching`, `billing`, and `notifications`. Each entry contains `name`, `sourceSHA256`, and `keys`, where `keys` is the bytewise sorted exact key list. The parallel `secrets.<service>` chart reference must equal `release.runtimeSecrets.<service>.name`. Inspection, deployment, rollback, export, and restore validate the Helm entry against the live or archived Secret before using it.

If a derived Secret name already exists, root reads it before mutation and requires the exact namespace, name, labels, full annotation, sorted keys, decoded values, recomputed hash, and immutable state. A 12 character prefix collision, deleted and recreated Secret, changed label, wrong key set, mutable object, or byte difference fails without replacement. A stable foundation Secret mismatch also fails because changing its bootstrap values is a data replacement operation, not rotation.

Spec 0007 owns `deploy/production/rate-limit-evidence.schema.json` and both modes of `gateway/cmd/ratelimitevidence`. Spec 0006 consumes them. `task test:auth-rate-limit` creates `.tmp/production` when needed and removes only the canonical evidence file before its first check. It reads the seven required production rate values from `deploy/helm/vermouth/values-production.yaml`, exports their exact environment names, and supplies them to the same parser the gateway uses at startup. After every command named in spec 0007 passes, it invokes the writer. The writer derives the Git SHA from the current checkout, rejects dirty rate limit inputs, asks the shared rate policy package for normalized minute first and hour second values, hashes the seven bytewise sorted `NAME=value\n` lines, and writes the canonical document.

The writer creates a unique temporary regular file in `.tmp/production`, sets mode `0644`, writes and syncs the bytes, closes it, rejects a symlink or nonregular destination, then replaces the destination with `os.Rename`. It syncs the containing directory where the operating system supports that operation and removes the temporary file on failure. A failed test or writer leaves no passing artifact. The verifier loads the original bytes, rejects a symlink or nonregular document, validates every field and derivation, serializes the parsed value with the same canonical encoder, and requires a byte for byte match. The GitHub workflow also validates the file against the committed schema, then adds the unchanged original bytes to the release bundle and uploads those same bytes as workflow evidence. It never copies from `.tmp/rate-limit-evidence.json` or rewrites the document.

The clean input set is `api/openapi.yaml`, `api/oapi-codegen.yaml`, `gateway/`, `web/src/api/`, `web/src/pages/SignInPage.tsx`, `web/src/pages/SignInPage.test.tsx`, `web/src/routes.tsx`, `web/src/routes.test.tsx`, `web/package.json`, root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `Taskfile.yml`, `.env.example`, `deploy/helm/vermouth/`, `deploy/production/rate-limit-evidence.schema.json`, and `test/authratelimit/`. Image publication keeps its separate image input cleanliness checks from **AC-4**.

### State transitions

1. Storage: `unselected` to `dedicated` or `os-fallback`, then `locked` before the first PV. A locked missing root becomes `blocked`, never another storage mode.
2. Certificate: `absent` to `staging proven` to `production ready`. Any failure keeps public HTTPS closed.
3. Release: `source` to `images verified` to `base inspected` to `migration compatible` to `mutation locked` to `foundation ready` to `migrations complete` to `application ready` to `external ready`. Any pending Helm state blocks `base inspected`. A migration failure records `migration partial` with the reached per service Goose versions while the previous application remains active.
4. Export: `running` to `local identity proven` to `quiesced` to `streaming` to `locally verified` to `archive ready` to `running`. Failure returns to the prior running state and reports an incomplete export.
5. Disaster bootstrap: `empty exact target` to `archive verified` to `manifest and configuration transferred` to `recorded platform ready`. Any existing Vermouth identity, PV, PVC, or component data blocks this path.
6. Restore: `running` to `local identity proven` to `archive verified` to `remote incoming` to `remote staged` to `preflight verified` to typed confirmation to `traffic closed` to `data restored` to `release restored` to `verified` to `traffic open`.

### Restricted SSH deployment protocol

The GitHub deployment key and the operator key are separate. GitHub uses only `vermouth-deploy` and forced command. Local `prod:doctor`, `status`, `logs`, `export`, `restore`, and `rollback` use the existing operator SSH configuration and never reuse the GitHub private key.

The authorized key line uses `restrict,command="/usr/local/sbin/vermouth-ssh-entrypoint"`. `vermouth-ssh-entrypoint` accepts only `inspect-base <git-sha> <github-run-id> <github-run-attempt>`, `preflight <git-sha> <bundle-sha256>`, and `deploy <git-sha> <bundle-sha256>`. `inspect-base` requires empty standard input and passes a schema version 1 request to the root program without creating a staging or release directory. The other actions require the release stream. `bundle-sha256` is SHA256 over the exact final `tar.zst` bytes computed by the GitHub runner after bundle assembly and checked by the entrypoint before decompression. The entrypoint rejects extra arguments, unknown commands, malformed run values, nonhex values, a Git SHA other than 40 lowercase hexadecimal characters, or a checksum other than 64 lowercase hexadecimal characters.

`inspect-base` is read only with respect to Kubernetes, Helm, Secrets, release directories, storage, and platform identity. It takes the shared production lock and fails while any mutation holds the exclusive lock. The root program reads live `helm history vermouth`. Any `pending-install`, `pending-upgrade`, `pending-rollback`, or `uninstalling` revision blocks inspection. Exactly one `deployed` revision is the baseline even when older failed or superseded revisions exist. When one exists, the program reads that exact revision through `helm get values --revision`, resolves `release.identity` to `/var/lib/vermouth/releases/<git-sha>/<github-run-id>-<github-run-attempt>`, verifies every stored evidence checksum, verifies the stored source Git SHA, and validates every fixed `release.runtimeSecrets` entry against the referenced live Secret name, annotation, labels, sorted keys, and immutable state before reading all four live Goose versions. No Helm history returns the all null previous identity tuple and four zero Goose versions only when no `vermouth` application resource and no applied Goose version exists. Helm history with no deployed revision, more than one deployed revision, a missing or mismatched runtime Secret, or an unreachable database fails inspection. A failed first install must be cleared through an operator reviewed Helm cleanup after `task prod:status` proves there is no live application or applied Goose version. `inspect-base` never performs that cleanup. `/etc/vermouth/platform.json` is a cross check only. A nonempty cached current revision or release identity that disagrees with live Helm state fails inspection rather than replacing the live source. Failed, pending, uninstalling, and superseded Helm revisions are never the migration baseline.

`deployment-base.json` contains only the fields in the schema table above. `previous_application_revision` means the application revision active before this candidate. It is not `previous_deployable_revision`, which remains the newest older rollback target after a successful release.

GitHub streams one `tar.zst` release bundle over stdin. The entrypoint hashes the raw stream before extraction, writes it under `/var/lib/vermouth/releases/.incoming/<github-run-id>-<github-run-attempt>`, rejects links and paths outside the staging directory, and permits only `images.json`, `deployment-base.json`, `rate-limit-evidence.json`, `migration-compat-evidence.json`, `bundle-manifest.json`, `values-production.yaml`, and `chart/`. It verifies every file checksum from `bundle-manifest.json`, then atomically renames the directory to `/var/lib/vermouth/releases/<git-sha>/<github-run-id>-<github-run-attempt>`. The immutable release identity is `<git-sha>/<github-run-id>-<github-run-attempt>`. An existing final directory is accepted only when the raw bundle checksum and every file checksum match, otherwise the run fails without replacement.

Schema version 1 `images.json` contains `schema_version`, `git_sha`, `github_run_id`, `github_run_attempt`, `generated_at`, `chart_sha256`, and an `images` object keyed by the fixed 11 workload names. `git_sha` is the full checked out commit from `git rev-parse --verify HEAD^{commit}` and must equal the commit resolved from the requested workflow ref. `github_run_id` and `github_run_attempt` come from the matching GitHub workflow context and are stored as decimal strings without a leading zero. `generated_at` is the GitHub runner UTC clock captured after every image passes registry inspection and immediately before the document is written, formatted as RFC 3339 with whole seconds and `Z`. `chart_sha256` comes from `platformconfig tree-sha256 deploy/helm/vermouth`, using a `vermouth-tree-v1` byte stream with sorted slash separated file paths and, for every regular file, the path, permission bits masked to `0777`, and exact committed bytes encoded with the scalar rules from spec 0005. Links, nonregular files, untracked files, and a dirty chart tree fail.

Each image requires `repository`, `tag`, `digest`, `platforms`, `build_input_sha256`, `source_revision`, and `created_at`. `source_revision` equals the top level full `git_sha`. `build_input_sha256` is exactly 64 lowercase hexadecimal characters from the sole production image plan. `tag` must equal `git-` plus the first 12 characters of `source_revision`, plus `-`, plus the complete `build_input_sha256`. The repository must equal `docker.io/<DOCKERHUB_NAMESPACE>/vermouth-<workload key>`. `digest` is the authoritative root OCI index digest in `sha256:<64 lowercase hexadecimal characters>` form. `platforms` is exactly the sorted JSON array `["linux/amd64","linux/arm64"]`. `created_at` equals the one UTC timestamp written to the root index and both child manifests for a new image, or the preserved annotation read from all three documents when an existing tag is reused. The root deployment program recomputes this identity, fetches the tag and then the index by recorded digest, validates the two child manifests and annotations, and confirms pull access before Helm. Helm receives only `repository@digest` references.

`platformconfig production-images-document <metadata-json> <verified-records-jsonl>` is the sole writer of `images.json` on standard output. Metadata contains only `git_sha`, `github_run_id`, `github_run_attempt`, `generated_at`, and `chart_sha256`. Each verified record supplies exactly the per image fields above plus the inspected root `digest` and `created_at`. The command requires all 11 workload records exactly once, validates every derivation, and emits UTF8 canonical JSON with object keys in lexical order, no insignificant whitespace, and one trailing line feed. Generated Helm values store `release.gitSHA`, `release.githubRunID`, `release.githubRunAttempt`, `release.identity`, `release.imagesJSONSHA256`, `release.deploymentBaseSHA256`, `release.migrationCompatEvidenceSHA256`, `release.rateLimitEvidenceSHA256`, and `release.bundleManifestSHA256`. The root deployment program computes these checksums from the validated files and passes them as runtime Helm values. `release.bundleManifestSHA256` is never written inside a file covered by that same manifest, which avoids a circular checksum. These values are part of the Helm revision history. Status, inspection, rollback, export, and restore resolve a Helm revision to its immutable release directory through these stored values, then verify every exact checksum before using any release record.

After `inspect-base`, GitHub stores the exact returned bytes as `deployment-base.json` and uploads the file as a workflow artifact. `platformconfig production-migration-set-sha256 <repository-root>` is the sole producer of the candidate migration set SHA256. It hashes the fixed service order `identity`, `teaching`, `billing`, `notifications`, then each service's sorted `db/migrations/` paths, permission bits masked to `0777`, and exact committed bytes through a `vermouth-migrations-v1` canonical byte stream. A link, nonregular file, untracked file, dirty migration tree, missing service, or empty migration set fails.

`task test:migration-compat -- deployment-base.json` validates the base document and its correlation to the current GitHub run. When the previous tuple is null, it applies the candidate migration set to four empty test databases. When it is nonnull, it checks out `previous_source_revision` into a temporary clean Git worktree and prepares each test database at the version recorded in `previous_goose_versions`. For every later candidate migration, the target applies exactly one version, rejects any SQL file containing Goose directive `-- +goose NO TRANSACTION`, then runs the previous revision's store and model integration tests against that intermediate schema. After every step passes, it applies the remaining services in the same way and runs the candidate migration tests against all four final schemas. Removing, renumbering, or changing a migration already present in `previous_source_revision` fails before database setup. The target writes `migration-compat-evidence.json` only after all four databases and every intermediate version pass. The evidence contains only the fields in the schema table above.

Before the first production migration Job, root writes schema version 1 `/var/lib/vermouth/reports/migration-<github-run-id>-<github-run-attempt>.json` atomically. It contains `release_identity`, `started_at`, nullable `finished_at`, `previous_goose_versions`, `candidate_goose_versions`, `reached_goose_versions`, and status `running`, `passed`, or `failed`. The release and version targets come from the validated bundle, timestamps come from the VM UTC clock with whole seconds and `Z`, reached versions come from live `goose_db_version`, and status comes from the bounded Job outcomes. Root refreshes the report after every committed migration and writes the terminal status before releasing the mutation lock. This report is operational evidence only. It never authorizes a different release.

The final bundle carries the exact base document and evidence. `preflight` validates their schemas, byte checksums, correlation fields, base SHA256, per service Goose versions, and bundle manifest coverage. `deploy` takes the exclusive production mutation lock before it resolves the live deployed Helm revision and database versions. It requires the same previous revision, release identity, source revision, `images.json` checksum, and Goose version map before its first Kubernetes, Helm, Secret, or platform identity mutation. A mismatch means the base became stale. The deployment stops before Secret creation, foundation reconciliation, or migration and the workflow must restart from `inspect-base`. One noncancelling concurrency group `production-<GITHUB_REPOSITORY>` covers image publication, inspection, compatibility testing, bundle creation, and deployment. The VM lock protects every mutation, including operator commands outside GitHub.

### Export archive contract

The encrypted export contains one zstd frame whose plaintext is one POSIX tar stream. Archive paths are slash separated UTF8 relative paths. Each path must already equal its normalized form, must be unique after normalization, and may not be empty, absolute, `.`, contain `..`, contain a backslash or zero byte, or escape its declared root. Directory and regular file entries are the only accepted types. Symbolic links, hard links, devices, FIFOs, sockets, sparse entries, extended attributes, access control lists, and global tar metadata are rejected. Entries are ordered by UTF8 path bytes.

The archive contains exactly these roots:

1. `manifest.json`.
2. `releases/current/`, copied byte for byte from the immutable directory named by the current Helm application revision.
3. `releases/previous/`, copied byte for byte from the newest earlier deployable revision, or absent only when the manifest previous release value is null.
4. `config/production.env`.
5. `postgres/identity.dump`, `postgres/teaching.dump`, `postgres/billing.dump`, and `postgres/notifications.dump` in PostgreSQL custom format.
6. `helm/foundation.json` and `helm/application.json`, captured from the exact live revisions.
7. `storage/postgres-identity/`, `storage/postgres-teaching/`, `storage/postgres-billing/`, `storage/postgres-notifications/`, `storage/redpanda/`, `storage/garage-metadata/`, `storage/garage-data/`, and `storage/traefik-acme/`.
8. `secrets/runtime/`, containing one canonical snapshot for every unique runtime Secret referenced by the current and optional previous application revisions.

Each retained release directory includes its `.bundle-sha256`, `images.json`, `deployment-base.json`, `rate-limit-evidence.json`, `migration-compat-evidence.json`, `bundle-manifest.json`, `values-production.yaml`, and complete chart. Restore maps it back to `/var/lib/vermouth/releases/<release-identity>` only after both the outer export manifest and the release's own evidence checks pass.

Each runtime Secret snapshot path is `secrets/runtime/<secret-name>.json`. It is canonical schema version 1 JSON with exactly `schema_version`, `service`, `name`, `source_sha256`, `keys`, and `values`. `keys` is the sorted exact key set. `values` maps each key to its decoded UTF8 value. Export derives the expected inventory from `release.runtimeSecrets` in the retained live Helm revisions, deduplicates identical names, reads only those live Secrets, compares their exact metadata and decoded bytes, recomputes `vermouth-secret-v1`, and writes a snapshot only on a complete match. A missing, extra, duplicate, or mismatched referenced Secret aborts export before the final archive exists.

`manifest.json` is canonical schema version 1 JSON. It contains `created_at`, `hostname`, the exact locked storage identity, `current_release`, nullable `previous_release`, `goose_versions`, `roots`, `regular_file_bytes`, and `files`. Each release value contains its identity, Helm revision, every stored release evidence checksum, the workload to image digest map, and the fixed runtime Secret evidence map copied from that Helm revision. `roots` is the exact sorted list above, with the optional previous root governed by `previous_release`. `files` maps every regular archive path except `manifest.json` to an object containing its nonnegative byte `size` and SHA256. `regular_file_bytes` is the exact sum of those sizes. A listed file must exist, every regular file must be listed exactly once, and each checksum covers the exact uncompressed file bytes. The manifest is validated before any restore mutation, then the streaming validator bounds each entry and the total by those sizes, hashes every regular entry, and requires an exact match.

Storage directories preserve numeric user, group, permission mode, and whole second modification time. Restore applies those values only beneath the selected empty component directory. Metadata and `secrets/runtime` directories become root owned mode `0700`; metadata and runtime Secret snapshot files become root owned mode `0600`; restored immutable release directories become root owned with write bits removed. `config/production.env` is always installed as root owned mode `0600`. Restore does not apply archive ownership or modes to any path outside these fixed roots.

### Production mutation lock

`/run/lock/vermouth-production.lock` is the single VM lock. Root opens it mode `0600`. `inspect-base` takes a nonblocking shared `flock` for its full read. `prod:bootstrap`, `deploy`, `prod:rollback`, `prod:export`, and `prod:restore` take a nonblocking exclusive `flock` before they inspect mutable state and hold it through their final readiness, recovery, and platform identity update. Failure to acquire the lock changes nothing and reports that another production mutation is active. `prod:status` and `prod:logs` do not mutate state and may run without the lock. Status uses a nonblocking shared probe to report only `free` or `busy`. A process exit releases the kernel lock. No stale lock cleanup command is needed.

`/etc/sudoers.d/vermouth-deploy` permits exactly `/usr/local/sbin/vermouth-deploy-root` with no command line arguments. The forced entrypoint sends one validated schema version 1 request JSON on stdin. The root program validates it again and reads release content only from the fixed release directory. Bootstrap installs both root owned programs mode `0755`; deployment bundles cannot replace them.

Port 22 remains an operator owned Azure network rule while temporary SSH deployment exists. `PasswordAuthentication` and `PermitRootLogin` are off. The restricted key allows no PTY or forwarding. Rotation adds the new public key and GitHub Secret, proves one deployment, then removes the old authorized key line. The old private key is deleted from GitHub after that proof. Migration to Azure OIDC removes the restricted key and user only after an OIDC deployment succeeds.

### Key invariants

3. Local and production use the same k3s version, packaged Traefik generation, chart, image set, Jobs, probes, and release order.
4. The selected storage root becomes immutable before the first PV exists.
5. A missing locked storage root starts no stateful workload.
6. Build and push finish before any VM state changes.
7. Database down migrations never run automatically.
8. Each service and migration Job receives only its own database URL. Only billing receives Garage credentials.
9. Public traffic reaches only Traefik on ports 80 and 443, then web or gateway.
10. Other applications on the VM are outside Vermouth ownership.
11. An application rollback never changes foundation data, database versions, broker events, or Garage objects.
12. Secrets never appear in Git, image layers, Helm values, command arguments, or logs.
13. `platformconfig production-image-plan` is the only producer of production build input hashes and tags.

15. A release directory is immutable and belongs to exactly one Git SHA, GitHub run ID, and run attempt. Helm history stores that release identity and its exact `images.json` checksum.
16. The migration baseline is the unique live deployed Helm application revision. Platform identity is only a cross check and a GitHub variable is never an authority for this value.
17. The previous application revision and its release identity, source revision, and images checksum are all null or all nonnull.
18. The root deployment program resolves the baseline again before its first Kubernetes, Helm, Secret, or platform identity mutation. Stale evidence starts no migration and changes no Secret or Helm release.
19. Every production mutation holds the one VM exclusive lock from its first mutable state read through readiness, recovery, and platform identity update. `inspect-base` holds the shared lock for its complete snapshot.
20. A pending Helm operation or history without exactly one deployed revision is never treated as a migration baseline. Only a completely absent and proven empty application returns `null`.
21. Every migration already present in the previous source revision is immutable. Each new migration is compatible with the previous application after that individual version commits.
22. Helm values anchor the exact `images.json`, `deployment-base.json`, rate limit evidence, migration evidence, and bundle manifest bytes. A release missing any checksum is not deployable or eligible for rollback.
23. An export contains the complete current and optional previous immutable release directories. Restore never invents a new release identity or reconstructs missing evidence from summaries.

27. A current or previous runtime Secret can be recreated only from its authenticated encrypted export snapshot. The current production environment never substitutes for an older rotated value.

### Security model

1. Friends reach only HTTPS. HTTP exists for ACME and redirect.
2. Google OAuth and session behavior remain spec 0004. Feature 21 rate limits are a hard launch prerequisite.
3. GitHub stores a temporary restricted deployment private key, Docker Hub push token, Docker Hub username, target host key, and `age` public recipient. It never stores `azureuser` credentials or production application values.
4. The VM deployment user cannot run a general shell through its deployment key. Root owns the validated deployment entrypoint and exact sudo rule.
5. `/etc/vermouth/production.env` is mode `0600`. Task reads it into Kubernetes Secrets without logging values.
6. Docker Hub uses a write token in GitHub and a separate read token in the VM pull Secret.
7. Vermouth Pods keep named ServiceAccounts, token mounts off, default deny NetworkPolicies, numeric users, read only root filesystems, dropped capabilities, no privilege escalation, and `RuntimeDefault` seccomp.
8. Compliance scope is ordinary tutor account and education records. No PCI, health, or regulated payment processing is introduced because payment state remains a manual tutor action.
9. The `age` private identity is an operator Mac secret containing exactly one native identity. Only its single derived public recipient may appear in configuration. Export writes no plaintext archive on the Mac. Restore may hold one root owned mode `0600` plaintext incoming or staged archive on the VM only while preflight and apply run, and removes it before returning.
10. Archived Docker Hub credentials are read inside the root restore process only after archive authentication and validation. They never appear in arguments, output, logs, Helm values, or a live shell environment that outlives the process.
11. Azure control plane inspection uses the operator's existing Azure CLI identity only for read operations against `PROD_AZURE_VM_RESOURCE_ID`. GitHub and the VM receive no Azure credential.
12. The full runtime Secret source SHA256 annotation is nonsecret integrity metadata. Namespace RBAC protects it from untrusted reads, while logs, status, and Helm values may show the hash but never decoded Secret values.
13. Runtime Secret snapshots exist only inside the authenticated encrypted export stream or its protected restore staging tree. They inherit the archive identity, mode `0600`, cleanup, and no plaintext Mac storage rules.

### Helm and Secret retention

Every application upgrade passes `--history-max 5`. A revision is deployable only when Helm reports status `deployed` or `superseded`, its stored release identity resolves to an immutable release directory, every stored release evidence checksum matches its exact file bytes, its fixed `release.runtimeSecrets` map is complete and agrees with every parallel chart Secret reference, every referenced live Secret matches the recorded name, full source hash annotation, sorted keys, exact labels, and immutable state, every image record has the canonical tag derived from its full recorded values, every tag resolves to its recorded root digest and provenance, every image digest remains pullable from Docker Hub, and matching migration compatibility evidence covers the recorded Goose versions. Platform identity records `current_application_revision` and `previous_deployable_revision` after external readiness.

`previous_application_revision` in migration evidence and `previous_deployable_revision` in platform identity are different values. The first is the unique application revision deployed when a candidate workflow inspects its base. The second is the newest older deployable revision retained for rollback after the candidate becomes externally ready. A successful deployment may turn its inspected previous application revision into the new previous deployable revision, but no command may substitute one field for the other before that transition completes.

Runtime Secrets carry labels `app.kubernetes.io/name=vermouth`, `app.kubernetes.io/component=runtime-secret`, and `vermouth.dev/runtime-service=<service>`. Annotation `vermouth.dev/source-sha256` carries the full 64 character canonical source SHA256. The Secret name keeps the first 12 hash characters as its immutable suffix.

Garbage collection starts only after external HTTPS readiness and the new platform identity are both durably recorded. Its authoritative keep set is the union of the complete `release.runtimeSecrets` maps from the live current deployed revision and newest earlier deployable revision. Before deleting anything, root lists namespace `vermouth` once and builds the complete candidate set. A candidate must have the exact application and runtime component labels, one fixed service label, matching `<nameBase>-<12-lowercase-hex>` name, valid full hash annotation whose prefix matches the name, and `immutable=true`. Any list error, missing keep reference, malformed candidate, duplicate service and name identity, or metadata mismatch aborts the complete cleanup before deletion. After that validation pass, root deletes only candidates outside the keep set. A delete error stops cleanup, reports the partial list, and leaves every remaining Secret untouched; any earlier deletion is still proven unreferenced. Decoy, foundation, ambiguous, current, and previous Secrets are never deleted. A failed upgrade or automatic Helm rollback performs no Secret garbage collection.

`prod:rollback` recomputes the previous deployable revision from live Helm history and required artifacts rather than trusting a cached number. It reads the release identity, all evidence checksums, and complete `release.runtimeSecrets` map from that Helm revision, opens only `/var/lib/vermouth/releases/<git-sha>/<github-run-id>-<github-run-attempt>`, and verifies every checksum and referenced live Secret before inspecting image records. It rejects a revision when any Secret name, full hash annotation, keys, labels, or immutable state differs, when any image tag does not recompute from its full `source_revision` and `build_input_sha256`, when the tag resolves to another root digest, or when registry provenance or child manifests differ. After rollback creates a new Helm revision and external HTTPS becomes ready, the command writes platform identity atomically from that live revision. If readiness or the platform write fails, the exclusive lock remains held while the command restores the prior application revision or reports a closed traffic state. The encrypted export includes `/etc/vermouth/production.env`, complete current and optional previous immutable release directories, and verified runtime Secret snapshots for both retained revisions, so restore preserves every retained Secret value, source hash, and release evidence file even if Kubernetes Secret objects and VM release directories were lost.

## Consequences

**Positive**:

1. Development and production share one chart, k3s version, packaged edge, release order, and image set.
2. The existing VM and a low cost disk avoid a new managed platform bill.
3. Private immutable images and restricted SSH make the temporary deployment path auditable and replaceable.
4. A manual encrypted export gives a real free recovery path.
5. Per revision Secret evidence detects recreated objects and lets an encrypted restore preserve both current and previous credential sets.

**Negative and tradeoffs**:

1. The one node VM is a single point of failure and has no automated backup.
2. The engineer chose automatic operating system disk fallback before first PV creation. A mistaken first bootstrap can therefore put production data on the nearly full shared disk. Platform identity prevents silent switching later, but it cannot make the initial fallback safe.
3. GitHub Actions holds a temporary SSH private key because the subscription cannot create the Entra application needed for OIDC.
4. File based Traefik ACME state requires one Traefik replica.
5. Manual export needs downtime, operator discipline, local Mac storage, access to the private `age` identity file, and periodic restore practice. Losing that identity makes every existing archive unreadable.
6. Private Docker Hub availability and limits become part of every deployment.
7. Every deployment adds one read only SSH round trip after image publication. A rollback or manual Helm change during the compatibility test invalidates the base and requires the workflow to rerun that test.
8. Production mutations are serialized on the VM. A second deploy, rollback, export, or restore fails fast while another mutation is active instead of waiting in an invisible queue.
9. Migration compatibility takes longer because the previous application tests run after every new committed migration version. That cost buys a checked promise that a partial migration failure leaves the active application usable.
10. Doctor now depends on the operator's Azure CLI session for a read only control plane check. An expired or wrong session blocks bootstrap and deployment even when SSH still works.
11. Exports are larger because they retain two complete release evidence directories, but those files are small beside the stateful storage and preserve the existing trust model after restore.
12. Export and restore must validate and carry decoded runtime Secret snapshots. Those bytes increase the consequence of losing the `age` identity or mishandling a decrypted stream, so the existing authenticated streaming and plaintext cleanup rules remain mandatory.

**Neutral**:

1. Other applications on the VM are neither a Vermouth dependency nor a Vermouth management target.
2. There is no application database migration for deployment metadata.
3. The local registry remains a development detail. Production pulls Docker Hub digests.
